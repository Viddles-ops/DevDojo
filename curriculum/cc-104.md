# Microtasks, decisions, handoffs: the operator workflow

Sessions end; work doesn't. The operator system (`_operator\` in the
Projects root + the `chief-operator` agent) exists so that any session —
today's or a cold one next month — can pick up in minutes. Four mechanisms
carry the weight.

## 1. The loop: Orient → Decide → Decompose → Lane → Execute → Gate → Record

The two ends are the point. **Orient** means establishing state from files
and `git status`, never from memory — and, on any repo you engage, running
the **substrate check**: does it have a `CLAUDE.md` module map, a runnable
test suite, and a living roadmap? Those three set the working mode —
*autonomous* (all present), *supervised* (partial: every diff is shown to
Nate and each session adds one substrate task), or *substrate-first* (no
`CLAUDE.md`: the only allowed work is creating it). If the record and the
disk disagree, disk wins, then fix the record. **Record** means the session
isn't done when the code works; it's done when BACKLOG.md, DECISIONS.md, and
HANDOFF.md say so.

The middle three steps decide *how* the work runs. **Lane** picks the path:
the **direct lane** (the operator implements it itself) is allowed only for a
small, safe change — ≤3 files, ≤~150 lines, no new module boundaries, no ADR
implicated, tests present — and **everything else is the pipeline lane**,
which gets a written plan in `_operator\plans\`, a **plan gate** (a fresh
agent that did *not* write the plan critiques it), and a fresh executor fed
only the plan plus the project's `CLAUDE.md`. When in doubt, pipeline.
**Execute** does the work in the chosen lane. **Gate** is the non-negotiable
finish line: the **diff gate** reads the *entire* diff, runs the full test
suite, and confirms the roadmap is still accurate before anything is called
done. Two hard rules live here — consensus is not correctness, and you never
merge on a reviewer's approval alone with tests failing or absent. Every new
behavior ships with a test that fails if it breaks; a diff that adds behavior
without one is rejected at the gate.

## 2. Microtasks: small, one deliverable, provably done

Every task on `BACKLOG.md` has an ID (`DOJO-012`), **one** concrete
deliverable, and a **done-check** — a command or observable output that
settles "is it done?" without opinion. Size cap ~30 minutes; bigger gets
split. Why this beats "improve the quiz feature": a vague ask has no
finish line, so it balloons; a microtask with a done-check is verifiable
by someone who didn't do the work.

## 3. ADRs: decide once, in writing

`DECISIONS.md` holds one-line architecture decision records, appended *the
moment* a decision is made. Before starting anything, the loop checks it:
if an ADR already covers the approach, follow it — don't re-litigate
mid-project. ADRs also make decisions *criticizable*: ADR-020 (pushes go
through Git Credential Manager, PAT script retired) exists because a
failure was diagnosed once, and no future session has to rediscover it.

## Worked example: the DOJO-006 split

DOJO-006 said "quiz mode: parse questions, LLM grades answers, score to
progress.json." Picked up, it was sized at *three* concerns — engine
module, routes+UI, live end-to-end — too big for one microtask. The
workflow response, in order:
1. **Decide first:** ADR-022 fixed the contract (function signatures, the
   JSON verdict shape, the progress.json schema, degradation behavior)
   *before any code*.
2. **Split:** DOJO-006a/b/c, in dependency order, each with its own
   done-check (006a: pytest + a live grading call; 006b: page renders with
   Ollama stopped; 006c: the original end-to-end check).
3. **Execute and record:** one dedicated commit per microtask, each
   leaving the system working; statuses moved as they closed.

## 4. Handoffs: write for the cold reader

Before a session ends, prepend to `HANDOFF.md`: what got done (IDs +
outcomes), what's in flight (exact file/branch state), the single best
next action, ADRs added, and warnings. Quality bar: **a cold session can
resume in under two minutes of reading.** Everything has exactly one home
— handoffs point to facts, they don't duplicate them.

## Try it

Open `_operator\HANDOFF.md` and read only the top entry, then answer: what
would you do next, and what would you *not* need to rediscover? Then find
DOJO-006's split in `BACKLOG.md`'s Done section and match each sub-task to
its done-check.

## Quiz

1. What three things must every microtask have, and which of them makes
   "done" a fact instead of an opinion?
2. When is an ADR written, and what does the loop do with existing ADRs
   before new work starts?
3. In the DOJO-006 example, what was produced *before* any implementation
   code, and why did that come first?
4. A change touches five files and adds a new module. Which lane does it go
   in, what artifact does it need before code, and what must the diff gate
   confirm before it can be called done?
