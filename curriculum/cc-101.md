# Claude Code fundamentals: sessions, CLAUDE.md, and the operator

## What Claude Code is

A terminal/desktop app where you describe work in plain English and Claude
reads files, writes code, and runs commands — with your permission. Each
conversation is a **session**. Sessions don't share memory with each other,
which is the central problem this workspace's setup solves.

## CLAUDE.md — the project's brain

When Claude Code starts in a folder, it automatically reads `CLAUDE.md`
there. That file is the project's technical reference *written for Claude*:
architecture, module map, deploy commands, gotchas. Your best example is
`po_intake_automation\CLAUDE.md` — it even has a table of "if you changed
file X, redeploy Y."

**Rule of thumb:** anything you had to explain to Claude twice belongs in
CLAUDE.md. Then you never explain it a third time.

## Agents — specialists you can summon

An agent is a markdown file in `~\.claude\agents\` with a role, rules, and
tool access. You have two:

- **chief-operator** — runs the show: reads the handoff, breaks work into
  microtasks, checks the decision log, routes work to the right model.
- **deploy-guard** — owns backups, deploy records, and rollbacks via the
  DeployGuard CLI.

Invoke one by naming it: *"chief-operator: what's next for OSKA?"*

## The operator workflow (why sessions don't start cold)

The `_operator\` folder is shared memory between sessions:

| File | Question it answers |
|---|---|
| `HANDOFF.md` | What happened last session? What's next? |
| `BACKLOG.md` | What tasks are open, in what state? |
| `DECISIONS.md` | What approaches are already decided? |

The loop: **start** by reading the handoff → **work** microtasks → **end**
by writing a handoff. Skip the last step and your work is invisible to the
next session.

## Try it

Open `_operator\HANDOFF.md` and read the top entry. Could you resume that
work from it alone? That's the quality bar every handoff should meet.
