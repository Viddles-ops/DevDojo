# Custom agents: chief-operator and deploy-guard dissected

A custom agent is just a markdown file in `C:\Users\natee\.claude\agents\`.
You have two, and they're opposite species — which makes them a perfect
anatomy lesson. Every agent file has the same three organs:

## 1. Frontmatter — the routing surface

```yaml
---
name: deploy-guard
description: Backup, deployment-tracking, and restore agent... Use when
  the user asks to back up projects, record a deployment, roll back...
tools: Bash, PowerShell, Read, Grep, Glob
---
```

The `description` is not documentation — it's the **trigger**. Claude reads
it to decide when to hand work to this agent, so it's written as matching
rules ("Use when the user asks to..."). Two optional keys do real work:
`tools:` is a capability allowlist — deploy-guard gets five read/run tools
and **no Edit or Write**, so the backup steward physically cannot rewrite
your code. `model:` — chief-operator says `inherit`, meaning it runs on
whatever model the session already has.

## 2. Body — the doctrine (this becomes the system prompt)

The body *is* the agent. Compare the two:

- **chief-operator** is an *orchestrator*: broad territory, a startup ritual
  (read HANDOFF, then BACKLOG), an operating loop (Orient → Decide →
  Decompose → Delegate → Verify → Record), and a routing table that sends
  work to *other* agents by task shape. Its job is judgment.
- **deploy-guard** is a *specialist*: one toolkit (`python -m deployguard`),
  a command list, and numbered operating rules. Its job is wrapping one
  dangerous capability safely.

## 3. Guardrails — live where the danger lives

deploy-guard's rules are absolute and local to it: never `--yes` past a
REINVENTION RISK warning, never restore without explicit confirmation of
project + tag, never touch the HIPAA repos' .gitignore. Putting the
guardrails *inside the agent that owns the risky tool* means every caller —
you, chief-operator, a future session — inherits them for free.

Two design rules fall out of the dissection: **subagents start cold** (no
conversation memory), so a definition must carry its own context — note how
both files hardcode absolute paths rather than assuming the agent knows
them. And **least privilege beats trust**: the narrower the agent's job,
the shorter its `tools:` list should be.

## Try it

Open both files in `C:\Users\natee\.claude\agents\`. For each, answer: what
sentence in the `description` would cause Claude to pick it? Then find the
one rule in deploy-guard that requires a human in the loop no matter what.

## Quiz

1. What does the frontmatter `description` actually control, and how does
   that change how you should write it?
2. deploy-guard's tools list omits Edit and Write. What class of failure
   does that prevent, even if its instructions were ignored?
3. Why do both agent files spell out absolute paths instead of saying "the
   projects folder"?
